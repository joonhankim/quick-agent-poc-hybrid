# HD현대 법무 지원 AI Agent — 문제 정의서

---

## 1. 무엇을 (What)

### 1.1 풀고자 하는 문제

**기업 법무팀의 법률 정보 접근 비효율**

기업 법무 담당자가 업무 중 특정 법령의 조문, 적용 범위, 위반 시 제재 등을 확인해야 할 때, 현재는 다음과 같은 과정을 거칩니다:

1. 법제처 사이트에서 해당 법령을 직접 검색
2. 수십~수백 개 조문 중 관련 조항을 수작업으로 탐색
3. 관련 시행령/시행규칙까지 교차 확인
4. 해석이 필요한 경우 외부 법률 자문을 별도 요청

이 과정에서 **법령 텍스트 자체에 대한 접근과 해석**이 병목이 됩니다. 법률 전문가가 아닌 법무 실무자에게 조문 원문의 의미를 빠르게 파악하는 것은 반복적이고 시간 소모적인 작업입니다.

### 1.2 만들고자 하는 것

**법령 조문 전문을 기반으로 질의응답하는 RAG 기반 AI Agent**

- 사용자가 자연어로 법률 질문을 입력하면
- 대한민국 현행 법령 1,001건의 조문 전문에서 관련 조항을 시맨틱 검색하고
- AI 에이전트가 검색 결과를 분석하여 출처가 명시된 법률 정보를 제공하는 시스템

### 1.3 해결하지 않는 것 (명시적 범위 제외)

| 항목 | 제외 사유 |
| :--- | :--- |
| **법률 자문** | AI의 법률 자문은 법적 책임 문제가 있으므로, 일반적인 법률 "정보 제공"만 수행. 모든 응답에 면책 고지문 필수 포함 |
| **판례 분석** | 법제처 Open API가 판결 전문(판시사항, 판결요지)을 JSON으로 제공하지 않아 구조화 수집 불가. 사건명만 인덱싱됨 |
| **사내 규정 검색** | 현재 데이터 소스는 공공 법령만 대상. 사규/내규 연동은 별도 데이터 파이프라인 필요 |
| **영문 계약서 분석** | 현재 인덱스는 한국 법령만 포함. 영문 법령/계약 분석은 데이터 확장 시 가능 |

## 2. 왜 (Why)

### 2.1 비즈니스 관점

**법무 업무의 구조적 비효율**

기업 법무팀의 업무는 크게 **조사(Research)**와 **판단(Judgment)**으로 나뉩니다. 현재 법무 담당자의 시간 중 상당 부분이 "어떤 법령의 몇 조가 이 상황에 적용되는지"를 찾는 **조사** 단계에 소비됩니다.

이 조사 단계는:
- 반복적이고 패턴화된 작업 (동일 법령을 다른 맥락에서 반복 조회)
- 법률 전문 지식보다 **검색과 독해** 능력에 의존
- AI가 대체하기 가장 적합한 영역

AI Agent가 조사 단계를 대행하면, 법무 담당자는 **판단과 의사결정**에 집중할 수 있습니다.

### 2.2 기술적 관점

**범용 AI의 법률 도메인 한계**

일반 LLM(ChatGPT, Claude 등)에 법률 질문을 하면 다음 문제가 발생합니다:

| 문제 | 설명 |
| :--- | :--- |
| **환각(Hallucination)** | 존재하지 않는 조문 번호나 법령명을 생성 |
| **출처 부재** | "~법 제N조에 따르면"이라고 하지만 실제 해당 조문과 불일치 |
| **시점 불일치** | 학습 데이터 기준 시점의 법령을 인용하여 현행법과 다를 수 있음 |
| **기업 보안** | 외부 SaaS에 법무 질의 내용이 유출될 위험 |

RAG 기반 시스템은 이 문제들을 다음과 같이 해결합니다:

- **환각 억제**: 실제 법령 조문 텍스트를 검색하여 근거로 제공하므로, LLM이 근거 없는 내용을 생성할 여지를 줄임
- **출처 명시**: 검색된 법령명, 조항 번호를 응답에 포함하여 검증 가능성 확보
- **현행법 기반**: 인덱스에 적재된 현행 법령 데이터를 기준으로 응답
- **Azure Private 환경**: 모든 데이터와 LLM 호출이 Azure 내부 네트워크에서 처리

### 2.3 데이터 관점

**왜 법령 조문 전문인가**

공공 법률 데이터 중 구조화된 수집이 가능하고, RAG에 적합한 텍스트 밀도를 가진 소스를 선정했습니다.

| 후보 데이터 | 수집 가능성 | 텍스트 밀도 | 채택 여부 |
| :--- | :---: | :---: | :---: |
| 법령 조문 전문 | O (법제처 API → JSON) | 높음 (평균 6,388자) | **채택** |
| 판례 전문 | X (JSON 미제공, HTML만) | - | 제외 |
| 판례 사건명 | O | 극히 낮음 (~20자) | 인덱싱만 |
| 사내 규정 | 별도 파이프라인 필요 | 다양 | 향후 과제 |

법제처 Open API의 법령 API는 조문 전문을 JSON 필드로 제공하여 자동화된 수집이 가능합니다. 반면 판례 API는 상세 조회 시 판결 전문(판시사항, 판결요지)을 JSON으로 제공하지 않아 구조화 수집이 불가능합니다. 이것이 "법령 조문 전문 1,001건"만으로 RAG를 구성한 핵심 이유입니다.

## 3. 어느 수준까지 (To What Extent)

### 3.1 기능 수준

| 기능 | 목표 수준 | 현재 달성 |
| :--- | :--- | :--- |
| 법률 질문 의도 분류 | 키워드 + LLM 이중 경로로 분류 정확도 확보 | O |
| 법령 조문 검색 | 시맨틱 하이브리드 검색으로 관련 조항 상위 5건 반환 | O |
| 법률 분석 응답 | 조문 인용 + 해석 + 출처 명시 + 면책 고지 | O |
| 일반 대화 | 법률 외 질문에 대한 자연스러운 대화 | O |
| 멀티턴 대화 | 이전 맥락을 유지한 후속 질문 처리 (최근 10턴) | O |
| 응답 품질 보증 | 불완전 응답 자동 감지 및 재시도 (최대 1회) | O |
| 실시간 스트리밍 | 토큰 단위 SSE 스트리밍 + 중간 상태 메시지 | O |
| 대화 영속성 | 서버 재시작 후에도 이전 대화 복구 가능 | O |

### 3.2 품질 수준

**응답 품질 기준:**
- 모든 법률 응답에 **근거 법령명과 조항 번호**가 포함되어야 함
- 모든 법률 응답에 **면책 고지문**이 포함되어야 함
- "죄송합니다", "답변을 드릴 수 없습니다" 등 **회피성 응답은 자동 재시도** 대상

**응답 품질이 아닌 것:**
- 법률적 정확성에 대한 보증은 하지 않음 (법률 자문이 아님)
- 조문 해석의 법적 구속력은 없음

### 3.3 데이터 수준

| 항목 | 수준 |
| :--- | :--- |
| 인덱스 총 건수 | 6,001건 (법령 1,001 + 판례 5,000) |
| RAG 활용 데이터 | 법령 조문 전문 1,001건만 |
| 조문 본문 보유율 | 94.4% (500자 초과) |
| 평균 content 길이 | 6,388자 |
| 법령 유형 커버리지 | 법률, 시행령, 시행규칙, 규칙, 규정, 직제 등 7개 유형 |
| 데이터 갱신 주기 | 수동 (자동 갱신 파이프라인 미구축) |

### 3.4 보안 수준

| 항목 | 수준 |
| :--- | :--- |
| 시크릿 관리 | Azure Key Vault (운영), .env (로컬) |
| 네트워크 | Azure Private 환경 내 통신 |
| 로그 보안 | API 키/엔드포인트 마스킹, 기술적 에러 사용자 미노출 |
| 데이터 유출 방지 | 외부 SaaS 미사용, Azure OpenAI 내부 엔드포인트 |
| CORS | 허용 도메인 제한 (운영 환경 도메인 등록 필요) |

### 3.5 성능 수준

| 항목 | 수준 |
| :--- | :--- |
| 라우팅 | 키워드 매칭 시 즉시, LLM 분류 시 ~1초 |
| 법률 응답 (첫 요청) | Azure Search + CrewAI 2-agent 순차 실행 |
| 법률 응답 (캐시 히트) | sub-second (Crew 결과 캐시 1시간 TTL) |
| 일반 대화 | LLM 직접 응답 (RAG 없음) |
| 동시 요청 | async/await 기반 비동기 처리 |

### 3.6 하지 않는 수준 (Non-Goals)

| 항목 | 설명 |
| :--- | :--- |
| 법률 자문 | 개별 사안에 대한 법적 판단이나 권고를 제공하지 않음 |
| 판례 분석 | 판결 전문 데이터 부재로 판례 기반 분석 불가 |
| 실시간 법령 업데이트 | 법제처 API 주기적 동기화 파이프라인 미구축 |
| 다국어 지원 | 한국어 법령만 대상 |
| 문서 업로드 분석 | 사용자가 계약서 등을 업로드하여 분석하는 기능 미포함 |
